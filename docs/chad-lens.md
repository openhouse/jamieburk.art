# Professional Legibility Lens

Use this as a public-safe internal editorial standard for making Jamie legible
to hiring, referral, civic-tech, and technical-operations readers.

## Core Rule

Make the unusual work institutionally legible without flattening its purpose,
agency, or ethics.

## Review Checklist

1. Minimize reader burden.
2. Make Jamie visible as the actor.
3. Say toward what end the work existed.
4. Use action verbs.
5. Translate insider terms.
6. Explain what became usable.
7. Avoid unsupported ownership claims.
8. Use collective-work language when work was collective.
9. Do not let tools or archives make Jamie disappear.
10. Do not publish private, unapproved, or exact claims without approval.

## Preferred Verbs

- built
- co-built
- created
- stewarded
- synthesized
- structured
- translated
- coordinated
- documented
- maintained
- supported
- contributed to
- helped teams use

## Translation Examples

| Avoid or explain | Use instead |
| --- | --- |
| under-structured | ambiguous, loosely defined, early-stage, resource-constrained, complex |
| tracking | structured, synthesized, maintained, coordinated, surfaced, stewarded |
| lightweight | practical, low-overhead, easy-to-adopt |
| data | open-data workflows, dataset documentation, source maps, public guidance, analytics, data-product requirements |
| maintainers | community platform operators, calendar editors, local stewards |
| AI-ready | human-reviewed AI-assisted workflows, source-backed documentation, reviewable AI support |

## Final Test

Would a busy hiring manager understand the work without needing Jamie in the
room to decode it?

## Proof Bank Tie-In

Use `docs/proofs-bank.md`, `docs/public-claims-inventory.md`, and
`apps/www/src/data/proofs.ts` as the public-safe claim layer. The website may
simplify or sequence claims for a specific audience, but it should not
strengthen them beyond the proofs bank without adding public-safe support and a
boundary first.
